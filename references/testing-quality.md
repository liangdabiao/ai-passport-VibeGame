# 验证与质量体系（宿主门禁 / 预览 / 自检 / 方法论）

> 这是三个案例最大的共性、也是"高质量"的直接来源。PokeWalk 135 个 verify_* 门禁、Spire 315 项启动自检 + PC 端 UI 巡检 + 2304 局平衡模拟、官方 validate.sh 三档门禁——**验证文化，不是验证动作**。

## 1. 三条原则（一切做法的出发点）

1. **能在宿主上验的，绝不留到设备上**（设备一轮几十秒观测弱；宿主几百毫秒工具全）。
2. **能在编译期挡住的，绝不留到运行期**（运行期在设备上，而设备上你看不见）。
3. **观测手段必须能看见目标故障——这一条要显式验证**（"测了没问题"和"测不到问题"在报告里长得一模一样）。

## 2. 分层验证矩阵

| 层 | 手段 | 位置 |
|---|---|---|
| 编译期 | `_Static_assert`（布局不变量/存档偏移/枚举-资源数量） | 固件源码 |
| 纯逻辑 | 宿主 `cc` 编译真 .c + 行协议对账 verify_*.py | tools/pipeline/ |
| 呈现层 | PC/Web 预览截图 + 布局巡检断言 | tools/inspector 或 tests/host/ui_preview |
| 整机 | 启动只读自检 + 串口截图/按键注入 | 固件 + tools/device |
| 发布 | 官方校验器 + SHA256 + 真机回归清单 | tools/release |

## 3. 宿主门禁骨架（verify_*.py 标准范式）

```python
# 内嵌 C 主程序 #include "被测模块.c"（不是替身！）
# "替身一旦与真的不同，对账全绿而固件全错。这是整个门禁体系里最容易犯且后果最大的错"
# cc -O1 -Wall -Wextra -Werror —— 宿主编译比目标编译更严
# 驱动是行协议：stdin 命令+参数，stdout 值+fflush；Python 侧比对
```

**逐值而非抽样**："嵌入式的数值缺陷典型形态是『差一点但一直差』——除数抄成 3、截断方向反了，分布上只差一两个百分点，抽样统计过得去，逐值立刻红。"

覆盖清单：常量逐一 / 定义域全量（uint8 就 0..255）/ 每个分段边界三点 / 溢出邻域钉钳制值 / **锚点**（人工算过的具体值——逐值对账验"两边一致"，两边同源同错它全绿，**锚点是唯一能挡住这个的**）。

体量参考：PokeWalk verify_battle 791 组 / verify_nurture 3201 拍 / verify_transitions 134400 格 / verify_audio 76985 样本。

## 4. 门禁三律（每条都有真实事故背书）

1. **反向验证**：故意改坏被测代码必须退出码非 0。"恒绿的门禁比没有门禁更坏——它让后面每轮都误以为验过了。"
2. **二阶陷阱**：反向验证先**断言改坏生效**（diff 非空）再看退出码——sed 模式没命中、副本没变、门禁照常绿，"验证门禁的手段自己恒绿了"。
3. **被测文件缺失时也必须红**（ALLOW_MISSING=1 可显式容忍未开工期）——"'还没做'和'做对了'不能是同一个信号"。

## 5. 观测手段五问（拿到任何验证手段先问）

- **Q1** 目标故障现在就发生，我的输出会变吗？（观测点必须在故障点**之后**——截图取字节序交换前就永远看不见字节序错）
- **Q2** 我的观测动作会改变被观测状态吗？（复位测衰减=每次测初始值）
- **Q3** 采样率/分辨力够吗？（定量算：帧率/传输字节/波特率/超时，不估）
- **Q4** 故障表现形式在我的通道里存在吗？（像素问题不指望日志、时序问题不指望单帧截图）
- **Q5** 如果它永远不报警，我怎么知道是"没问题"还是"坏了"？（= 反向验证）

三种失效形态实证：观测绕开出错环节（DMA 竞争紫屏但截图取交换前数据）/ 观测扰动状态 / 原理上无分辨力（跨帧中间态四条通道全不可见）。

## 6. 静态扫描门禁（verify_layout.py 三律）

解析源码 `#define`/常量数组/循环域，对绘制调用坐标求值检查横带不变量：
1. 无法静态求值的**显式报 SKIP 并打印**，绝不静默通过（"被检查的 bug 的成因就是越界像素静默丢弃——检查器自己不能犯同一个错"）。
2. 退出码只由确定违规决定，SKIP 不计失败（否则永远红然后被忽略）。
3. **豁免必须带理由、绑定行号、逐条打印**（代码一挪豁免就失效，有意如此）；"绝不允许为了让门禁变绿而加豁免"。

## 7. 启动自检（真机上、游戏前、只读）

Spire `game_self_test_run(seed)` 模式：

```c
static void check(report, condition, category) {
    report->checks++;
    if (!condition) { report->failures++; report->failure_mask |= category; }
}
// 失败不阻断启动，只打位掩码日志（PASS 打 checks=315，FAIL 打 mask）
```

构成参考：路线穷举生成校验（128 种子×2）、内容表完整性（事件 id 存在/label 非空）、数值锚点（金币/价格）、编解码往返、状态机端到端（走"开始→选职业→地图→战斗→暂停"→存档编码→解码→恢复→逐字段比对）。**大对象 calloc 防栈溢出**（main 栈只有 3584B）；种子外置（日期），换种子换一批检查。

## 8. UI 巡检（PC 端"截图回归测试"，Spire 模式）

同一份 game_app.c 在 PC 用 LVGL 渲染（host CMake + 桩 + `CARDGAME_LVGL_PREVIEW=1`）：
- 循环 18 页 + 10 步真实流程，每页导出 PNG。
- `--strict-layout` 断言（全部可复用）：
  - 任何可见对象不出屏、不出父容器（大背景豁免）
  - label 高度 ≥ 字体行高（防截字）；任意两 label 不重叠
  - 每页"应有/不应有标题栏"期望表；image scale_x==scale_y（禁拉伸）
  - 全屏背景 (0,0) 铺满且不透明（防白闪回归）
  - 特定页内容断言（第 6 页必须有"熔岩史莱姆"）
- 设备端无调试入口：巡检只存在于 PC。

## 9. 平衡模拟（游戏性也能自动化）

Spire `test_game_balance.c`：256 种子 × 3 策略 × 3 职业 = **2304 局自动对战**（跑真实状态机整局），断言首章完成率/通关率/第三章生命中位数/回合数/金币。"数值平衡不靠感觉，靠分布断言。"

## 10. 串口观测通道（真机自助验证）

- **截图**：`@@SHOT 240 320 rgb565be 80` + 每带 base64（76 字符/行防丢行）→ screenshot.py 收 PNG。回调式不缓存整屏。
- **按键注入**：`walk.py --keys e,c,A --settle N`（小写单击/大写双击）；**--settle 按最长动画给足**（战斗最坏 43.2s）。
- 边界：截图抓不到动画中间态；证明"画出来"≠证明"用对数据源"（换 sprite 要两图对比+bbox 度量）。

## 11. 验证报告模式（reports/）

- 按主题命名 `<topic>-<date>.md` + `evidence/` 存截图/JSON 回执。
- 报告末尾附表：逐条标注"我的手段能不能看见这条结论的反例"，三档**可信 / 量级估计 / 未验证**。
- **"没测到"与"没发生"必须分开写**。

## 12. 什么项目值得这么做（避免过度工程）

**值得**（满足两条以上）：有可对账的数值逻辑（"差一点不会崩只会一直错"）；有呈现层（故障形态是"不对"而非"崩"）；生命周期超几周或要交接；有可作基准的参考实现。

成本量化：单个门禁 100~400 行 Python+内嵌 C；反向验证每个 ~10 分钟；**观测通道（截图+按键注入）一次性各 ~150 行，是收益最高的一笔**；布局静态扫描 ~200 行抓到 3 处真缺陷；编译期断言每处 1 行几乎免费。

**不要做的**：不为"体验够不够好"造门禁（产品判断）；没有基准不推逐值对账；不为凑覆盖率给平台层写门禁。

## 13. 反面清单（照抄进任何项目）

| 看着对其实无效 | 正确做法 |
|---|---|
| 门禁全绿就放心 | 反向验证 |
| sed 改坏做反向验证 | 先 diff 断言改坏生效 |
| 门禁断言"调用了某函数" | 断言输出性质 |
| 不变量写在注释里 | _Static_assert 或门禁 |
| 截图当动画/时序证据 | 状态轨迹日志+帧号 |
| 截图当"用对了数据源"的证据 | bbox 等可量化特征 |
| 自检通过当"画对了" | 渲染改动必须看屏幕 |
| 越界静默丢弃 | 计数器 |
| 拿不到锁就读旧值（无影子副本） | 独立影子副本 |
| 慢操作放临界区 | 挪锁外 |
| 对账基准本身缺内容 | 基准缺口清单+死字段检测 |
| 手画素材凑数 | 同源同管线 |
| 相信协调者给的数字 | 关键数字自己复核 |
